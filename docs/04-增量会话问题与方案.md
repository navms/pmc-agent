## 4.2 导出：动态列与 OSS 链接

### 4.2.1 问题：Excel 列是固定的

**现象：** 用户问「导出列不要写死」。固定表头无法覆盖「这次查了哪些字段」。

**根因：** 导出 Agent 把列名写在模板里，和查询结果 schema 脱钩。

**选定：** 列从本次查询结果动态生成，而不是在 Prompt 或常量里枚举。

**为什么：** 点查、汇总、支付单字段集合不同。列跟数据走，模型只需决定「导出什么」，不必背表结构。

### 4.2.2 问题：会话里塞文件还是只给链接

**现象：** 图表和 Excel 若当消息附件，会话体积和刷新回放都会变差。

**选定：** 上传对象存储（OSS），会话只存下载 URL；图表先出图再上传。

**为什么：** AG-UI 消息是给回放用的协议对象，不是网盘。二进制走对象存储，历史接口只回链接。

## 4.3 存储：DistributedStore 与 Chat CRUD 变薄

### 4.3.1 问题：Agent 状态放哪

**现象：** Harness 需要 `distributedStore`。本机文件在多实例或重启后接不上。

**选定：** MySQL `JdbcDistributedStore`（独立库 `agentscope`），filesystem 用 `RemoteFilesystemSpec`。

**为什么：** 会话闸、子 Agent 任务、远程盘都依赖同一套 store。聊天记录仍在业务库 `chat_session` / `chat_message`，不要和 Agent 内部 KV 混表。

### 4.3.2 问题：ChatSession / ChatMessage 分层过重

**现象：** 「CRUD 不要搞这么复杂，就操作 DO」。

**选定：** 会话消息走薄的 DO 读写，去掉为 Graph 时代准备的多余装配。

**为什么：** AG-UI 落库已经是「协议 Message JSON」。再套一层 Domain/DTO 转换，改事件字段时要改三处。聊天持久化的成功标准是回放一致，不是充血模型。

## 4.4 观测第一轮：OTEL、Prometheus、SkyWalking

### 4.4.1 问题：本机要能看见 Agent 调用

**选定：** `OtelTracingMiddleware` + Docker Compose 拉起 Prometheus / Grafana。用户看不懂空仪表盘时，补现成 Grafana 模板，而不是从零画图。

**为什么：** Agent 延迟来自模型、工具、子 Agent、HITL，单看应用日志分不清。OTEL span 是后续 Langfuse 的同一套语义。

### 4.4.2 问题：接到已有 SkyWalking 却「OAP 没有服务数据」

**现象：** 服务器 `111.229.7.178` 上 OAP 一直空；本机打点后 UI 404。

**根因（分层）：**

1. AgentScope 的 OTEL exporter 默认协议、路径与 SkyWalking OAP 接收端不一定一致；
2. 公网 IP 上的 UI 路径、OAP gRPC/HTTP 端口、采集器是否对公网开放，是运维问题，不是 Java 里再包一层就能好。

**试过：** 社区最佳实践、改 exporter、SSH 上服务器查。无法在对话里保证远端 OAP 一定收到。

**留下的工程结论：** 本仓库观测主路径后来收到 **Langfuse**（见 4.5）。SkyWalking 适合作基础设施 APM；Agent 的 prompt / generation input-output 更适合 Langfuse。两套可以并存，但不要用 SkyWalking 替代 generation 级观测。

## 4.5 Langfuse：本地部署、Span、Prompt Management

会话：[本地 Langfuse](d857fb00-1592-4994-a71d-a4662b547cac)。

### 4.5.1 问题：本机要有一套可点的 Trace UI

**选定：** `deploy/langfuse` Docker Compose；Agent 打 OTLP 到 Langfuse。

**中间件合并：** 用户要求 `LangfuseSessionMiddleware` 的 span 与 `OtelTracingMiddleware` 对齐，从而只保留一套。避免两个 middleware 各打一遍、session id 对不齐。

### 4.5.2 问题：Langfuse 里每次 model 的 input / output 都是 null

**现象：** Trace 树在，generation 空。

**根因：** 只挂了 Agent 生命周期 span，没有把模型请求的 messages / 完成内容写进 OTEL gen_ai 约定字段。Langfuse 靠这些字段填 Generation。

**选定：** 在 `onModelCall`（及同类钩子）把 input messages、output text、usage 写入 span。

**为什么：** 「能看见 Agent」不等于「能看见这一次 chat」。评测和点踩都依赖 generation 正文。

### 4.5.3 问题：Prompt 放代码里还是放 Langfuse

**选定：** `Prompt` 枚举保留 fallback 模板；启动时 `LangfusePromptService.compile` 拉远端（如 `pmc/supervisor`），失败则用本地。拉到的版本登记到 span，便于对照。

**代价：** 改本地 fallback **不会覆盖** 已 seed 的远端版本。改路由规则必须同步 Langfuse，否则现网仍跑旧稿。09-18 的意图澄清事故就是这个代价（见 4.9）。

### 4.5.4 其它

- 汉化：Langfuse UI 跟官方版本走，不在本仓库做翻译包。
- Unsafe 警告：来自 OpenTelemetry shaded JCTools，可忽略，不是业务错误。
- Prompt GET 失败：Langfuse 未起或 key/host 不对时要 fail-open 到 fallback，并打 warn。

## 4.6 Git 主干与未合入的 Python 沙箱

### 4.6.1 两特性分支合 master

仓库当时没有 `master`。`feat/langfuse-prompt-management` 已包含 `feat/spring-ai-alibaba-init` 并多一次 Langfuse 客户端提交。做法：从前者创建 `master`，推送后把 GitHub 默认分支改为 `master`，再删两个特性分支。

### 4.6.2 Python 执行工具（未合入）

计划曾是：独立 Docker 一次性容器跑 `python:` 镜像，工具挂父 Agent 并走 ASK HITL；**不要**把全局 `RemoteFilesystemSpec` 换成 Docker filesystem。该计划在会话中止于方案，**未作为现网功能合入**。银企查询仍走 Java Tool，不经 Python。

## 4.7 点踩写入 Langfuse Dataset

会话：[点踩与意图澄清](99b9b859-d760-4c61-bcb6-d366e9066406)。分支 `feat/session-thumbs-down-langfuse`。

### 4.7.1 问题：前端「踩」之后评测样本去哪

**现象：** 用户要在对话点踩，把**整次 session** 记到 Langfuse Dataset `base-case`。

**否决：** 只把最后一句 assistant 当样本（丢工具过程和子 Agent）；或把 Dataset 当聊天备份。

**选定：**

- 前端助手气泡「踩」→ `POST /sessions/{id}/feedback`；
- `ChatSessionAppService.dislike` 拉齐会话消息，经 `LangfuseDatasetClient` 建 item；
- 重复点踩要有业务错误码，避免刷同一 session。

**为什么：** Dataset 是评测集，不是日志。一条 item 应对应「用户怎么问、系统整段怎么答」，才能回归路由和工具对错。

## 4.8 意图澄清：为什么必须在中间件里做

### 4.8.1 问题：主 Agent 路由经常错

**现象：** 「有多少钱」被送进 `query_bank`（最多 10 条），再用自然语言心算合计。

**根因：** Supervisor 同时负责闲聊、路由、转述。把「query vs summarize」写在同一条 Prompt 里，模型仍会按字面「查询」走点查。控制面协议不能只靠主 Agent 自觉。

**选项：**

1. 再加一个用户可见的澄清子 Agent，让 supervisor `agent_spawn`；
2. 在 supervisor **进 ReAct 之前**用中间件改写本轮用户消息。

**选定 2。** `IntentClarifyMiddleware` 只挂在 `pmc_supervisor`；HITL 的 `approved`/`denied` 跳过。澄清 Agent **不**注册 `@AguiAgentId`，避免变成第二个对话入口。Supervisor Prompt 写明：不要 spawn `intent_clarify`。

**为什么：** 路由必须确定性发生在 spawn 之前。若让 supervisor 自己决定「要不要澄清」，失败模式和现在一样——它会直接 spawn 错的子 Agent。

### 4.8.2 问题：多轮「那这个账号呢」有没有历史

**现象：** `server-side-memory: false`，前端每轮往往只发**最新一句**用户消息。

**选定：** 中间件用 `RuntimeContext.sessionId` 读 MySQL `chat_message`（最近 20 轮 USER/ASSISTANT），去掉与本轮重复的最后一条用户原文，再送给澄清模型。

**为什么：** 指代消解需要上文账号和日期。不能指望 AG-UI 请求体自带全量历史。

### 4.8.3 改写格式

- `ready` → 用户消息变成 `【已澄清任务】` 块（意图、目标子 Agent、补全任务、原话）。
- `need_clarify` → `【意图澄清】` 块，禁止 spawn / 写工具，只追问一个问题。

Supervisor 必须按块执行。远端 `pmc/supervisor` 若没有这两段指令，改写等于白做。

## 4.9 结构化输出：`generate_response` 为什么「没了」

### 4.9.1 框架两条路径（以 AgentScope Java 2.0.3 `ReActAgent` 为准）

`call(msgs, IntentClarifyResult.class)` 会进 `doStructuredCall`：

| 条件 | 路径 | 模型看到什么 | `STRUCTURED_OUTPUT` 从哪来 |
|---|---|---|---|
| `supportsNativeStructuredOutput()` | native | `response_format` JSON Schema | 把**正文**当 JSON `fromJson` 写入 metadata |
| 默认（本仓库 DashScope **未**开 native） | fallback | 本轮临时工具 `generate_response` | **只有调用该工具成功**才写入 metadata |

`generate_response` 的参数是 `{ "response": <schema> }`，不注册进共享 toolkit，只存在这一次 call。

本仓库 `DashScopeChatModel.builder()` 没有 `nativeStructuredOutput(true)`。因此澄清走的是 **fallback**：工具会出现在 generation 的 `tools.count` 里。

### 4.9.2 问题：Trace 里有澄清 JSON，supervisor 却没用

Trace `7251648034895f5b3a4cfbcf8463e771`：

- 澄清 generation：`tools.count = 1`，但 `toolCalls` 为空；
- `output.text` 是整段 JSON；
- 随后 supervisor 的 USER 仍是原话，并 `agent_spawn query_bank`。

**根因分两层：**

1. **解析：** `classify()` 只认 `hasStructuredData()`。模型没调工具，正文 JSON 进不了 metadata，中间件 fail-open。
2. **Prompt：** Langfuse `pmc/intent_clarify` v3 要求「只输出一个合法 JSON 对象，不要额外文本」。这是在教模型走 native 正文，和 fallback 的工具路径对打。Few-shot 写成「输出：{...}」会强化这个行为。

所以不是工具注册丢了，是**模型被 Prompt 劝去不调工具**。

### 4.9.3 选定

代码：优先 `getStructuredData`；没有则从正文提取 JSON（纯 JSON、fence、夹在解释里的对象）。`maxTokens` 提到 1024，降低截断。

远端 Prompt：禁止「正文只输出 JSON」；明确「最终必须调用 `generate_response`，字段填在参数 `response`」。Few-shot **保留**，但每例写成「调用 generate_response，response 为 {...}」，不要写成助手正文输出。改完要重启，因为 Prompt 在启动时 compile。

**为什么双保险：** 现网模型仍可能把 JSON 写在 text 里。只改 Prompt 不够；只改解析会让错误 Prompt 一直活着。两条都要。

## 4.10 澄清过程要让用户看见，但不能破坏 AG-UI 生命周期

### 4.10.1 问题：澄清时前端一片空白

**现象：** 中间件里 `classify().block()`，父事件流要等澄清结束才出现 `RUN_STARTED`，用户以为卡住。

**否决：** 把 `intent_clarify` 注册成 Harness 子 Agent、做成 `query_bank` 那种嵌套卡片。代价是：事件 `source` 标记、`generate_response` 在 UI 暴露、supervisor 可能真去 spawn 它、`streamEvents` 与 `call(Class)` API 对不齐。

**选定：** 仍中间件驱动；用 AG-UI `CUSTOM`：`intent_clarify.start` / `intent_clarify.end`。前端 `clarifying` 显示「正在进行意图澄清…」。run 结束 / abort / error 时清掉。

### 4.10.2 问题：`First event must be 'RUN_STARTED'`

**现象：** 先发 `CUSTOM`，AG-UI 客户端 `verifyEvents` 拒绝。

**根因（协议，不是前端写错）：**

- [ag-ui `verify.ts`](https://github.com/ag-ui-protocol/ag-ui/blob/d53c4ef6/sdks/typescript/packages/client/src/verify/verify.ts)：第一条只能是 `RUN_STARTED` 或 `RUN_ERROR`；run 未结束时第二条 `RUN_STARTED` 也会报错。
- [AgentScope Java AG-UI](https://java.agentscope.io/v2/en/integration/protocol/agui.html)：`RUN_STARTED` 只由 `AgentStartEvent` 转换，**不会**像 Python runtime 的 `_ensure_run_started_event` 那样自动补发。
- `intentClarifyMiddleware` 在洋葱链最内层，`next` 即 `buildAgentStream` core，core 的第一件事才是 `AgentStartEvent`。

**选定：** 中间件先发一次 `AgentStartEvent`，再 `CUSTOM start` → classify → `CUSTOM end` → `next.apply(改写后的 input).filter(e -> !(e instanceof AgentStartEvent))`，避免二次 `RUN_STARTED`。Java 适配器用请求里的 `runId`，不依赖 `AgentStartEvent.replyId`。

HITL 与非 supervisor 不注入这些事件。

## 4.11 Seed 时间随机化

**现象：** `BankMockDataSeedIT` 写入时间不够随机，评测和演示容易撞同一天。

**选定：** 按工作日推进随机时间，而不是同一时钟戳加噪声。

## 4.12 增量后仍存在的债

- 写操作仍 mock；HITL pending、导出索引仍可能在内存。

- 点踩 Dataset `base-case` 仍无成功标准；回归用 `pmc-golden`（见 4.14）。

## 4.13 可以复用的增量原则

1. **观测字段要按消费方约定写。** Langfuse Generation 要 messages；空 span 没有评测价值。
2. **Prompt 版本是现网行为。** fallback 只保证能启动，不保证和 Langfuse 一致。
3. **结构化输出认的是路径，不是「看起来像 JSON」。** DashScope 未开 native 时，必须调 `generate_response`；few-shot 不能示范正文 JSON。
4. **控制面改写放在 ReAct 之前。** 澄清是中间件，不是又一个用户可聊的 Agent。
5. **多轮槽位读业务库历史。** 不要假设前端每轮带齐上下文。
6. **AG-UI 自定义事件只能出现在 `RUN_STARTED` 之后。** 中间件抢跑会直接被客户端掐死。
7. **要让用户知道系统在干什么，不必把内部 Agent 做成子卡片。** start/end CUSTOM + loading 更便宜，也更不容易污染生命周期。
8. **Java 版 AgentScope 没有的类，不要按 Python 文档硬接。** `RunPythonCodeTool` 即一例。

## 4.14 Agent Eval Harness

对照测评文档的 Task / Trial / Grader / Transcript / Outcome。pmc-agent 是对话与执行混合型：澄清补槽后 spawn 只读子 Agent，或父 Agent 写工具 + HITL。

完整流程、指标公式、SSE 观察与当前实现缺口见 [05-Agent回测实现](./05-Agent回测实现.md)。本节只保留对照表与启动命令。

### 4.14.1 两套 Dataset

| Dataset | 来源 | 是否自动打回归分 |
|---|---|---|
| `base-case` | 会话点踩整段 messages | 否。无 `successCriteria` 的 item 只作失败回流候选 |
| `pmc-golden` | 仓库 `eval/golden/golden-tasks.json` seed | 是。必须带可验证成功标准 |

点踩原轨迹常常是错路由，不能当 `ground_truth`。要进入 Golden Set，需人工钉 `expectedOutput.successCriteria`。

### 4.14.2 Task schema

`input.turns` 为用户轮次。`expectedOutput.successCriteria[].kind`：

- `required_agent` / `forbidden_agent`：业务子 Agent 集合（`query_bank`、`summarize_bank`、`export_excel`、`create_chart`）
- `required_write_tool` / `forbidden_write_tool`：父 Agent 写工具
- `interrupt`：是否必须 HITL
- `required_clarify` / `clarify_only`：意图澄清是否出现、本轮是否禁止 spawn

只标不可省略动作，不锁逐步调用顺序。`weight=high` 的写操作失败单独计数，不能被平均分稀释。

第一版分层约 16 条：闲聊、点查、汇总（含「有多少钱」禁点查）、导出、图表、缺槽澄清、多轮换账号、支付/同步 HITL。

### 4.14.3 怎么跑

现网同一入口 `POST /agui/run`。每个 Trial 新建 `chat_session`。HITL 默认 `resume approved=false`（断言的是中断，不是支付成功）。

```bash
mvn -pl pmc-agent-starter spring-boot:run -Dspring-boot.run.arguments=--pmc.eval.enabled=true
```

可选：`PMC_EVAL_MAX_ITEMS`、`PMC_EVAL_TRIALS`、`PMC_EVAL_RUN_NAME`、`PMC_EVAL_LIST_BASE_CASE=true`（只列出无标准的点踩 item）。

报告写到 `data/eval/<runName>.json`（`EvalRunSummary` + `EvalRecord`）。分数经 langfuse-java SDK 写到对应 Session（`langfuse.session.id` = 评测会话 id）。0.3.0 SDK 没有 Dataset Run / traces list，因此不另写 Dataset Run。

### 4.14.4 分数与失败分类

规则 Grader，无 LLM-as-Judge。

| 指标 | 分母 |
|---|---|
| `task_complete` | 全部 successCriteria 通过则为 1 |
| `tool_precision` | 实际 spawn+写工具 中属于 required 的比例 |
| `tool_recall` | required 被命中的比例；required 为空时为 1 |
| `tool_set_match` | 实际集合与 required 完全一致 |
| `unnecessary_call_rate` | 实际中不在 required 的比例 |
| `e2e_latency_ms` | Trial 墙钟 |

`errorCategory`：`wrong_agent`、`tool_missing`、`hitl_skipped`、`clarify_miss`、`harness_error` 等。`rootCauseLayer=HARNESS` 的超时/SSE 失败不记成路由错误。`trials>1` 时汇总 `pass@k` / `pass^k`。
